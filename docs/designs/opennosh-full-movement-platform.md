# CEO Plan: opennosh Full Movement Platform

Generated by `/plan-ceo-review` on 2026-08-22

## Vision

opennosh becomes the public gathering place and open protocol for trustworthy food data. People can find and verify food records without an account, contribute evidence from ordinary packaging, organize work around real data gaps, govern disputed records in public, publish independently maintained data packs, and reuse the commons through stable developer tools.

The website must make the word “commons” structurally true. Git remains the source of truth for accepted data and decisions. The public interface makes that system legible to people who do not use Git.

### 10x Check

The 10x version is not a larger centralized nutrition database. It is a federated, evidence-backed network in which a cuisine community, university, nonprofit, public agency, or independent maintainer can own a compatible pack, prove its lineage, coordinate improvements, and distribute it through opennosh without surrendering control.

Every loop is visible:

1. A real-world label or trusted source becomes evidence.
2. Evidence becomes a reviewed contribution.
3. Accepted contributions become versioned pack releases.
4. Packs become searchable records, downloads, APIs, SDKs, and embeds.
5. Declared reuse becomes visible public impact.
6. Gaps discovered through search and reuse become new commons missions.

### Platonic Ideal

A first-time visitor understands opennosh in seconds and can search immediately. A contributor can scan a package, verify extracted fields, and submit a reviewable change without understanding Git. A steward can see why a record changed, compare evidence, resolve a dispute, and publish a reasoned decision. A developer can install a typed SDK or pack, run locally, and preserve attribution by default. A community can maintain its own signed pack while participating in a shared index. The interface feels alive because every activity signal represents accepted work, never invented engagement.

## Product Outcome

opennosh succeeds when a person can move from curiosity to trustworthy data, then from trustworthy data to contribution or reuse, without encountering an account wall or an opaque administrative system.

The tracker remains a useful attached product, but the public commons becomes the primary role of `opennosh.org`.

## System Authority and Data Ownership

“Git is the source of truth” applies to accepted public artifacts, not every transient application state.

| Data class | Authoritative store | Examples | Mutation and deletion rule |
|------------|---------------------|----------|----------------------------|
| Accepted public record | Pack Git repository | Foods, nutrients, provenance, licenses, accepted corrections | Changes only through reviewed commits; prior versions remain in history. |
| Governance record | Pack or registry Git repository | Decisions, appeals, steward assignments, quarantine reasons | Append or supersede through reviewed commits; never silently edit history. |
| Federation trust metadata | Registry Git repository plus signed release metadata | Pack roots, release manifests, revocations, compatibility declarations | Versioned and signed; clients reject rollback, expiry, or invalid signatures. |
| Operational workflow | PostgreSQL | Accounts, drafts, review queues, rate limits, abuse restrictions, mission proposals | Mutable under authorization and audit logging; deletion follows account and retention policy. |
| External evidence | Private object storage outside the webroot | Rewritten package images and OCR inputs | Content-addressed, access-controlled, retained or removed under the evidence policy below. |
| Derived projection | PostgreSQL/search index/cache | Search documents, activity events, pack health, aggregate metrics | Rebuildable from canonical artifacts and operational events; never treated as canonical evidence. |
| External declaration | PostgreSQL with audit history | Voluntary reuse registry entries and verification state | Owner-editable, steward-verifiable, removable, and never promoted to verified without evidence. |

### Canonical Flow and Reconciliation

```text
Contributor evidence
        │
        ▼
Private object storage ──▶ PostgreSQL draft/review state
        │                              │
        │ evidence hash/reference      │ accepted decision
        └──────────────────────────────┘
                                       ▼
                              Git commit + pack release
                                       │
                    ┌──────────────────┼───────────────────┐
                    ▼                  ▼                   ▼
              Search index      Accepted events     Registry metadata
                    │                  │                   │
                    └──────────────────┼───────────────────┘
                                       ▼
                            Public site, API, SDKs
```

- Pending and rejected submissions remain operational records and never appear as accepted food data.
- A merged commit and valid pack release create an idempotent accepted-event record keyed by repository, commit, pack, and record identifier.
- Reconciliation compares Git heads, signed release metadata, database projections, and search-index checkpoints at least every five minutes.
- Missing or stale projections are rebuilt from Git and signed metadata. The public UI labels stale data and suppresses unverifiable activity rather than guessing.
- A Git/registry signature conflict quarantines the release from installation and cross-pack search while the last verified release remains available.
- A database outage pauses submissions and dynamic activity but does not invalidate downloadable signed packs or static provenance pages built from the last verified release.
- Every projection stores its source commit and schema version so divergence can be located and repaired.

### Publication State Machine

```text
DRAFT → VALIDATED → IN_REVIEW → APPROVED_PENDING_PUBLISH
                                      │
                                      ▼
                                  COMMITTED
                                      │
                                      ▼
                                    SIGNED
                                      │
                                      ▼
                                  PUBLISHED → INDEXED
                                      │             │
                                      └──── retry ──┘

Any pre-publish state → REJECTED or CHANGES_REQUESTED
COMMITTED without valid signature → PUBLISH_BLOCKED
SIGNED without registry confirmation → PUBLISH_RETRYING
Published release later fails trust checks → QUARANTINED
```

- Steward approval creates `APPROVED_PENDING_PUBLISH`, not an accepted event.
- A durable PostgreSQL outbox records the intended Git mutation, expected base commit, evidence hashes, approving decision, idempotency key, and retry state in the same transaction as approval.
- The publisher creates the Git commit, verifies that the committed payload matches the approved payload, creates and verifies signed release metadata, and confirms registry publication.
- Only `PUBLISHED` creates the accepted event. Entering `PUBLISHED` requires the reviewed commit, signed release, independent RPO-zero Git/release copies, and immutable RPO-zero evidence copy to verify and acknowledge durable storage. `INDEXED` is a derived projection and may lag without changing canonical acceptance.
- Retries reuse the idempotency key and inspect Git and registry state before writing. A crash after any boundary resumes from the first unverified step instead of creating a duplicate commit or release.
- A changed Git base moves the item to `PUBLISH_BLOCKED` for revalidation. The UI tells the contributor that approval succeeded but publication is waiting; it never calls the record accepted early.
- Projection failure after publication exposes a degraded or stale state and retries from the accepted event. It never rolls back the canonical release solely because search indexing failed.

## Accepted Scope

### 1. Federated Pack Network

- Publish a versioned pack manifest and compatibility specification.
- Support cryptographically signed releases and maintainer identity.
- Provide a registry with version, license, language, provenance, health, and maintainer state.
- Validate packs automatically before discovery or installation.
- Preserve license boundaries and block incompatible silent combinations.
- Support selected-pack search, installation, updates, rollback, quarantine, and removal.
- Allow communities to retain their own repositories and governance.

### 2. Evidence-First Capture

- Support mobile camera and barcode capture.
- Extract nutrition and ingredient fields from images, with field-level confidence.
- Require contributor verification before submission; OCR or AI output never auto-publishes.
- Detect likely duplicates and conflicting records before pull-request generation.
- Preserve reviewable evidence while stripping EXIF and location metadata.
- Define image rights, retention, deletion, and contributor acknowledgement.
- Model draft, validation, review, accepted, rejected, and reopened states.

### 3. Commons Missions

- Derive proposed work from real search failures, incomplete records, and pack coverage gaps.
- Support missions by cuisine, locale, institution, dataset, or missing field.
- Require a steward, acceptance criteria, target dataset, and explicit lifecycle for every mission.
- Calculate progress only from accepted contributions.
- Support moderated community mission proposals and released mission packs.
- Exclude personal leaderboards, streaks, contributor geolocation, and health comparisons.

### 4. Public Stewardship and Dispute Resolution

- Define community member, reviewer, pack steward, and maintainer roles.
- Provide correction, dispute, evidence comparison, decision, appeal, and reopening flows.
- Store public reasons, timestamps, responsible stewards, and versioned decision records.
- Support conflicts of interest, reviewer recusal, abuse reports, and temporary restrictions.
- Provide stewardship queues with pending, blocked, disputed, and aging work.
- Prohibit invisible administrative edits and unexplained rejection states.

### 5. Developer Distribution Kit

- Publish a versioned OpenAPI contract and compatibility policy.
- Maintain JavaScript and Python SDKs with generated contract tests.
- Provide a CLI for search, validation, pack installation, updates, and export.
- Provide a read-only MCP server for compatible assistants and developer tools.
- Publish embeddable food and provenance cards without hidden tracking.
- Support local and self-hosted endpoints across tools.
- Include licensing and attribution automatically in records, SDK responses, and embeds.
- Provide starter applications and a declared integration gallery.

### 6. Public Reuse and Impact Map

- Provide a voluntary registry for applications, research, public programs, and community projects.
- Label reuse as verified, community-declared, or unverified.
- Show countries or broad regions only, never contributor or end-user locations.
- Aggregate downloads, API use, pack installations, and accepted contributions using documented metrics.
- Show pack dependency and reuse relationships.
- Provide removal, correction, and opt-out flows.
- Display honest empty states when verified reuse does not yet exist.

## Identity and Authorization Boundaries

Anonymous access means public reading has no account wall. Accountable mutations require identity.

| Action | Identity requirement | Authorization |
|--------|----------------------|---------------|
| Search, inspect provenance, download public packs | Anonymous | Public read |
| Save a private draft locally | Anonymous or signed in | Browser-local only when anonymous |
| Upload evidence or submit a contribution | Verified opennosh account using the existing authentication system | Contributor |
| Review a contribution or verify reuse | Verified account | Assigned reviewer or steward |
| Resolve disputes, quarantine a pack, restrict abuse | Verified account with strong re-authentication | Pack steward or registry maintainer, with audit reason |
| Register, sign, revoke, or transfer a pack | Verified maintainer identity plus signing authority | Pack maintainer threshold policy |
| Change registry trust roots or compatibility policy | Strong re-authentication plus threshold approval | Registry root maintainers |

- Roles are scoped to a pack or the registry, never global by default.
- Role assignment, revocation, recusal, restriction, and restoration are audit events with actor, reason, time, and scope.
- GitHub linking is optional. Non-technical contributors use the existing opennosh account flow and never need to operate Git directly.
- Account deletion anonymizes operational profile data where legally and technically possible. Accepted public contributions retain attributed or pseudonymous authorship and license history; this consequence is shown before submission.
- Rate limits, duplicate detection, verified contact, content limits, and steward escalation control spam. Privileged actions require re-authentication and cannot be performed from an anonymous session.

## Evidence Lifecycle Policy

- The browser accepts JPEG, PNG, or WebP only, with a 10 MB pre-processing limit and a 20 megapixel decoded-image limit.
- The service verifies file signatures rather than trusting the MIME header, generates a random storage name, strips metadata, rewrites the image, scans it, and stores it outside the webroot.
- Raw uploads are destroyed after safe rewriting. Reviewers access evidence through authorized, expiring URLs.
- Rejected or abandoned evidence is removed 90 days after final disposition. Accepted evidence is retained while it supports the current record and for one year after supersession, unless rights, safety, or legal requirements require earlier removal.
- Git stores only a content hash, evidence type, source description, redaction status, and authorized reference. Image bytes never enter Git history.
- If evidence is removed, the record retains its decision history and a tombstone explaining why the original image is unavailable. Removal never rewrites accepted Git history.
- Contributors acknowledge that they have the right to submit the image and are told the retention and attribution consequences before upload.
- Privacy or rights reports immediately restrict public access pending steward review. Evidence is private by default; public display is a separate reviewed decision.
- Self-hosted deployments may configure compatible object storage or disable image retention and use manual-entry evidence references. Manual entry remains the universal fallback.

## Disaster Recovery and Dependency Outages

| Asset | Protection | RPO target | RTO target | Degraded behavior |
|-------|------------|------------|------------|-------------------|
| Git repositories and signed pack releases | Independent remotes, immutable release copies, verified clones | 0 for published commits/releases | 2 hours to serve last verified release | Public read/download continues from verified artifacts. |
| PostgreSQL operational data | Encrypted point-in-time recovery plus daily cross-region backup | 15 minutes | 4 hours | Public canonical reads continue; sign-in, submissions, review, missions, and dynamic impact pause. |
| Draft evidence storage | Versioned encrypted storage, integrity inventory, replicated metadata | 1 hour | 24 hours | Draft review and new uploads pause; no draft can publish while evidence is unavailable. |
| Published evidence tier | Immutable independently durable copy verified during publication | 0 | 24 hours for restored access | Canonical records remain; evidence may be temporarily unavailable but cannot be lost without violating the publication invariant. |
| Search and activity projections | Rebuilt from Git, signed releases, and accepted-event outbox | Rebuildable | 4 hours | Direct pack lookup and downloads remain; search/activity show degraded state. |
| Registry operational state | Git-canonical trust metadata plus database backup | 15 minutes operational, 0 for signed metadata | 4 hours | Existing trusted packs continue offline; enrollment, health refresh, and revocation propagation pause. |
| Signing keys | Offline encrypted threshold custody; online role keys in managed secret storage | No silent loss accepted | Per role runbook | Publishing pauses; last verified releases remain; suspected compromise triggers quarantine. |

- Database and object-storage restore drills run quarterly. Full regional-loss and projection rebuild drills run twice yearly.
- Root-key recovery and maintainer-succession ceremonies run before federation beta and twice yearly thereafter.
- Application backups never contain plaintext signing keys. Losing fewer than the signing threshold uses normal rotation; losing threshold authority requires public recovery governance and explicit client re-enrollment rather than pretending continuity.
- Restore verification checks record counts, source commits, evidence hashes, outbox completion, role assignments, restrictions, and signed metadata before writes resume.
- Incident runbooks name the operator, communication channel, user-visible status, rollback boundary, and evidence-preservation requirement for each dependency.

## Federation Constitution

- Pack maintainers control their data, release timing, contributor policy, steward appointments, and repository governance.
- The opennosh registry controls only registry inclusion, compatibility labels, index visibility, and distribution of its own trust metadata. It cannot edit a remote pack.
- Objective quarantine triggers are invalid or revoked signatures, manifest/schema incompatibility, malicious payloads, license contradiction, replayed versions, or failure of mandatory integrity checks.
- Quality disagreements that do not violate the protocol are labeled and presented as variants; they do not justify central deletion of a pack.
- Every quarantine or delisting includes a public reason, evidence, affected versions, decision authority, and appeal path. Emergency quarantine is reversible and requires later threshold confirmation.
- Pack appeals are decided under registry policy. Pack communities retain authority over their own records, but cannot compel the shared registry to distribute an unsafe or incompatible release.

### Release Ledger Foundation

T34.5 begins with an additive PostgreSQL federation release ledger. It is an append-only operational
projection, not a new canonical release source. Each accepted row retains the exact maintainer-signed
statement and signature, the historical online role-key row, immutable repository and pack scope,
the governed publication receipt and accepted event, the manifest and receipt digests, and both
receipt-publication and verification times. Admission remains behind the isolated operator CLI.

Release admission serializes per repository/pack. An exact replay is idempotent only while its
signing key remains current; replay after rotation still fails as retired or untrusted. Reusing a
release version for different signed material fails closed. A candidate whose governed receipt is
not newer than the latest ledger row is a rollback, regardless of whether its opaque release label
looks numerically newer. This avoids inventing ordering semantics for release labels while preserving
the canonical publication chronology.

The original one-release pilot audit event stored only a redacted payload digest, so migration cannot
reconstruct its signed statement. The schema does not synthesize a trusted row. Existing public
artifacts and receipts remain unchanged; any later reconciliation must re-submit independently
verifiable signed input through a separately approved operator ceremony.

### Multi-Scope Operator Policy

T34.5b replaces the original global invitation slot with a bounded, reviewed operator allowlist of
one to 32 immutable federation scopes. Each entry binds the numeric GitHub account and repository
IDs to their canonical labels and one pack ID. Duplicate scopes and conflicting account,
repository, or pack identities fail configuration validation; the original five exact scope fields
remain a compatible one-entry mode and cannot be combined with the JSON allowlist.

Invitation admission serializes independently per repository and pack. Exactly one single-use
invitation may exist for each configured scope, so a same-scope race fails closed while unrelated
reviewed scopes can proceed. Every existing steward, Forge installation, role-key, expiry,
quarantine, revocation, and append-only audit control remains in force. The database downgrade
refuses to recreate the former global slot after more than one invitation exists; it never discards
scope history. This policy change does not enroll a maintainer or expose federation through public
discovery, installation, ingestion, projections, or search.

### Signing and Recovery Model

Federation uses a TUF-style trust model rather than a single permanent signing key. Each pack publishes versioned root, targets, snapshot, and timestamp metadata. Root keys are kept offline where possible; online release roles use separate keys; sensitive roles support threshold signatures. Clients ship or explicitly trust pack roots, reject expired or rolled-back metadata, and can verify downloaded releases offline from bundled metadata.

Key rotation and maintainer succession require a valid threshold of the current root. If the complete signing threshold is lost, normal rotation is impossible: the registry quarantines the pack, publishes a recovery case and replacement root, and requires every connected administrator to approve an explicit trust reset. Clients keep the last verified release and never auto-trust the replacement; offline clients remain frozen until their operator imports and approves the recovery bundle. Malicious or disputed recovery remains rejected. Compromise drills must demonstrate rotation, revocation propagation, rollback rejection, expired metadata handling, total-threshold loss, explicit re-enrollment, malicious-recovery rejection, and restoration from the last verified release before federation exits beta.

### Cross-Pack Identity and Conflict Semantics

- Every record has a stable namespaced identifier: `{pack_id}:{local_record_id}`. Packs never overwrite another pack’s identifier.
- Duplicate detection creates a separate equivalence cluster with evidence and confidence; it does not destructively merge records.
- Search groups likely equivalents but preserves source variants, licenses, and pack identities.
- User-selected pack priority determines default display. Without an explicit preference, opennosh uses a documented deterministic order based on exact locale match, verified release status, schema completeness, and stable identifier order. It never selects based on undisclosed commercial preference.
- Conflicting nutrient values remain visible as variants with source date and evidence. The interface never computes an unlabeled average.
- License compatibility is evaluated before combined export. Incompatible records may be searched side by side but cannot be emitted as one silently relicensed dataset.

## Scope Posture and Release Trains

All accepted capabilities remain in the program. They do not have to appear in one production deployment. The first public release is a vertical trust loop: one verified pack, public search and provenance, guided evidence contribution with manual fallback, steward review, signed release, and one reference reuse client. Later release trains add federation breadth, missions, remaining distribution surfaces, and impact once their preceding technical gates pass. These gates protect users; they are not a quiet mechanism for cutting accepted scope.

### Release-Train Promotion Criteria

Promotion means beginning the next train’s production rollout, not deciding whether an accepted capability still matters.

1. **Vertical trust loop → broader contribution:** observe at least 30 production days, 100 successful anonymous searches, 20 completed evidence submissions, two active stewards, 95% of published records projected within five minutes, no unresolved severity-one integrity incident, median final review below seven days, p90 final review below fourteen days, and zero unacknowledged submissions older than forty-eight hours. A paused item is excluded only when it has a public reason, responsible steward, and next-review date.
2. **Broader contribution → federation pilot and missions:** complete at least 50 accepted contributions across three recurring, measurable data gaps; maintain the review backlog within published capacity; pass the deletion, restore, dispute, and publication crash-boundary drills; recruit two independent pilot pack maintainers.
3. **Federation pilot → general federation enrollment:** operate two independent maintainers and at least three signed packs for 30 days; simulate online-key compromise, root rotation, maintainer succession, disconnected verification, rollback attempt, registry outage, and recovery; achieve zero unexplainable divergence and complete every quarantine/appeal exercise.
4. **Stable protocol → full developer distribution:** keep the OpenAPI compatibility gate green for two release cycles; ship one reference client; complete two external integration trials; demonstrate attribution and license preservation in every surface before releasing the second SDK, CLI, MCP, embeds, and starter applications.
5. **Demonstrated reuse → public impact:** register at least three independently verifiable adopters, meet the minimum privacy bucket, complete removal and false-claim drills, and publish metric definitions before showing aggregate impact.

If a target is missed, the owner extends the observation window or fixes the failing system. Missing a target does not permit fabricated activity, lowered privacy safeguards, or silent advancement.

### Promotion Metric Dictionary

All promotion metrics use server-confirmed production events. Internal, staging, synthetic-monitor, load-test, known crawler, and administrator-marked test traffic is excluded. Privacy-preserving actor keys rotate after the stated counting window and are not exposed publicly. Every result is reproducible from a versioned query stored with the release decision.

| Metric | Canonical event and counting rule | Window and exclusions | Audit definition |
|--------|-----------------------------------|-----------------------|------------------|
| Successful anonymous search | Completed production search returning a valid response; deduplicate identical normalized query, pack set, locale, and privacy-preserving session within 30 minutes | Rolling 30 days; exclude bots, retries, prefetch, staff tests, and synthetic checks | Count deduplicated `search_completed` events with anonymous actor class and production flag |
| Completed evidence submission | Submission reaches `IN_REVIEW`; count one per contributor, evidence hash set, and target record | Rolling 30 days; exclude withdrawn duplicates, migration imports, staff fixtures, and automated replays | Count distinct accepted idempotency keys entering `IN_REVIEW` |
| Accepted contribution | Item reaches `PUBLISHED`; one per canonical commit, pack, and record identifier | Rolling 30 days; exclude projection retries and release rebuilds | Count distinct accepted-event keys whose signature and durable acknowledgements verify |
| Active steward | Authorized steward performs at least three substantive review or dispute actions on distinct submissions | Rolling 30 days; exclude self-review, automated actions, and reverted test decisions | Count distinct steward IDs meeting the qualified-action threshold |
| Projection within five minutes | Elapsed time from `PUBLISHED` timestamp to verified searchable projection | All published events in window; exclude documented full-outage intervals from the SLO denominator but report them separately | Numerator is projections at or below 300 seconds; denominator is all eligible published events |
| Review age | Time from `IN_REVIEW` to first substantive acknowledgement and to final disposition | Rolling 30 days; paused items excluded only with public reason, owner, and next-review date | Report median, p90, oldest unacknowledged, oldest active, and paused count |
| Recurring measurable data gap | Distinct schema-backed coverage query that remains below a published target across two weekly snapshots | Minimum two weeks; exclude one-off failed imports and unsupported fields | Count versioned gap definitions with snapshot queries and steward approval |
| Independent signed pack | Compatible pack controlled by a distinct administrative domain and maintainer authority | 30-day pilot; exclude mirrors, forks without independent governance, and opennosh-owned test packs | Count verified registry identities with distinct trust roots and ownership declarations |
| External integration trial | A non-opennosh operator completes install, authenticated or anonymous use as applicable, attribution verification, and failure-path test | Per protocol release; exclude internal starter apps and maintainer-operated demos | Count signed trial reports linked to tested client and protocol version |
| Verified adopter | Independent live project, publication, or signed institutional declaration reviewed under the reuse policy | Current release train; exclude community-declared-only, duplicate organizations, and inaccessible demos | Count active verified registry entries with evidence and reviewer decision |
| Severity-one integrity incident | Published wrong-pack, signature-bypass, irreversible evidence loss, cross-license leak, or unauthorized privileged mutation | Entire observation window; exercises and staging events excluded | Count incident records classified by the ratified severity policy; unresolved count must be zero |

Metric definitions are versioned. Changing a definition during an observation window restarts that metric’s window unless the old and new queries are proven equivalent. Promotion decisions store the query version, result snapshot, exclusions, and approving owners.


The OpenAPI contract generates shared clients so JavaScript, Python, CLI, and MCP surfaces do not become four hand-written protocol implementations. Each public surface still has its own usability and contract tests.

## Glossary

- **Accepted event:** an idempotent projection of a merged canonical commit and valid pack release, not a draft or unmerged submission.
- **Broad region:** country-level geography by default; a larger region when the privacy threshold is not met.
- **Compatible pack:** a pack whose manifest, schema, license declaration, signatures, and required validations satisfy the active registry specification.
- **Conflict:** two non-identical claims that refer to the same equivalence cluster and cannot both be selected under one stated context.
- **Evidence:** a source artifact or citation supporting a claim, stored with hash, type, rights status, provenance, and access policy.
- **Health:** current signature validity, schema compatibility, fetch freshness, validation outcome, and quarantine state; never an opaque popularity score.
- **Precedence:** deterministic presentation priority among variants; it never deletes or silently merges the lower-priority record.
- **Quarantine:** reversible registry exclusion of a release from installation and default search because a defined integrity or safety trigger fired.
- **Revocation:** signed withdrawal of a key, maintainer authority, or pack release from future trust decisions.
- **Verified reuse:** a reuse claim supported by a reviewable public artifact or signed declaration and approved by an authorized reviewer.
- **Air-gapped support:** pack search, provenance, validation, tracking, and offline verification operate without hosted services after required artifacts are installed; hosted OCR and public impact aggregation degrade to documented manual or unavailable states.

## Architecture Decisions

| Decision | Choice | Consequence |
|----------|--------|-------------|
| D8: Publication executor | Durable publication orchestrator with forge adapters | A dedicated worker consumes the PostgreSQL outbox and idempotently drives Git branch/PR creation, merge observation, signature verification, release publication, and projection triggers through GitHub, other forge, or local-Git adapters. |
| D9: Federated search | Local projection of verified releases | The registry ingests validated signed pack releases into a versioned rebuildable search projection; visitor queries never fan out to pack operators and every hit preserves pack, license, release, and provenance. |
| D10: Evidence storage | S3-compatible abstraction with immutable replication | Draft evidence uses private versioned object storage; publication requires a verified content-addressed copy in an independent RPO-zero destination. | D12: Background jobs | PostgreSQL-backed jobs with leased workers | Durable job and outbox tables provide idempotency, leased claims, bounded retries, backoff, heartbeats, named terminal failures, and operator-visible dead-letter queues across separate work lanes. |

The approval API never performs Git or signing side effects synchronously. The orchestrator verifies external state before every retry, stores step-level results, and resumes from the first unverified boundary. Adapter implementations share contract tests for branch creation, pull-request lifecycle where available, merge observation, transient failure, idempotent retry, and local or air-gapped operation.

Search ingestion verifies trust metadata, schema compatibility, license declaration, and content hashes before indexing. Projection versions record the source release set, expose ingestion lag, support atomic index swaps and rollback, and can be rebuilt without changing canonical pack data. Installed-pack-only search remains available for self-hosted and air-gapped deployments.

The evidence adapter contract covers validated upload, metadata-stripped rewrite, content hashing, private read authorization, immutable publish copy, durable acknowledgement, lifecycle deletion, tombstone, integrity inventory, and restore verification. Git stores hashes and governed references only; PostgreSQL stores workflow metadata only; neither stores image bytes.

The handoff is time-bounded, keyboard accessible, dismissible, and covered by analytics that count only whether migration guidance was shown or used, not tracker contents. Navigation, PWA metadata, documentation, tests, and release notes use `/tracker` as the canonical destination. The public homepage remains intentionally reachable for authenticated users.

Publication, evidence processing, pack ingestion, reconciliation, projection, and notification use distinct lanes with independent concurrency and retry policy. Workers are stateless and may scale horizontally; job payloads contain identifiers and versions rather than media or full records. A job cannot acknowledge completion until its external side effect is verified. Dead-letter entries retain failure class, attempts, context, next operator action, and safe replay controls.

### Module Boundaries

- `foods` owns canonical food schemas and read models.
- `evidence` owns media validation, storage references, OCR proposals, retention, and tombstones.
- `contributions` owns drafts, validation, duplicate candidates, review state, and publication intent.
- `governance` owns roles, decisions, disputes, appeals, restrictions, and audit records.
- `packs` owns manifests, licenses, compatibility, record identity, and local installation.
- `federation` owns registry trust, signing metadata, quarantine, enrollment, and cross-pack projections.
- `missions` owns gap definitions, proposals, lifecycle, and accepted-event progress.
- `publication` owns outbox orchestration, forge adapters, signature/release verification, and durable acknowledgements.
- `impact` owns declared reuse, verification, privacy thresholds, and aggregate projections.
- `tracker` consumes public food APIs and preserves its private user-data boundary; public commons modules never read tracker logs.

Domain modules may depend on shared schema, identity, audit, and job primitives. They may not import another module’s database tables directly; cross-domain mutations use explicit application services and typed events. Circular imports and shared catch-all utility modules fail architecture tests.

### Scaling and Failure Isolation

- At 10x load, add web and lane-specific worker replicas, read replicas where safe, CDN/static caching for public records, and independent search-ingestion concurrency. PostgreSQL leases prevent duplicate claims.
- At 100x load, partition accepted-event and job tables, isolate search infrastructure behind its existing projection contract, shard evidence processing by content hash, and extract a domain into a service only if measured contention requires it.
- PostgreSQL is the write-side single point for hosted workflow. Its outage preserves verified public reads but pauses mutations and dynamic operations under the documented RTO.
- Registry root authority is a human trust concentration. Threshold roles, offline keys, explicit recovery, independent pilot maintainers, and public decisions limit it.
- A forge outage pauses new publication but cannot invalidate the last verified pack release.
- Search-index failure degrades discovery but preserves direct record, pack, and download access from verified artifacts.
- Evidence-store failure blocks new publication rather than creating evidence-free accepted records.

### Rollback Posture

- Public-route, contribution, federation, mission, distribution, and impact releases use independent feature flags; disabling a flag must not delete accepted artifacts.
- Database changes are additive and backward-compatible until the rollback window closes. Destructive cleanup is a separate verified release.
- Search projection deployment uses versioned indexes and atomic alias swaps; rollback selects the previous verified index.
- Publication workers can be paused without losing leased or outbox work. A previous application version must tolerate new pending job types by leaving them unclaimed.
- A bad pack release is quarantined while clients retain the last verified release. Canonical Git history is corrected by a new reviewed commit, never rewritten as an operational rollback.
- A failed public-homepage rollout can disable the commons feature flag and temporarily serve a maintenance-safe homepage while `/tracker` remains stable.

## Error and Rescue Decisions

| Decision | Choice | Consequence |
|----------|--------|-------------|
| D14: Failure handling | Typed failure taxonomy with per-error rescue contracts | Every expected failure has a specific class, retry rule, attempt limit, backoff, terminal state, structured context, operator action, user message, and test. Catch-all handling may add crash context and re-raise only; it cannot swallow or generically retry. |
| D15: OCR failure | Best-effort OCR with immediate manual fallback | Timeout, rate limit, empty, malformed, or low-confidence OCR preserves evidence and opens manual entry; retries are optional and never overwrite contributor-confirmed fields. |
| D16: Duplicate-check outage | Accept submission and block publication | A contribution enters `DUPLICATE_CHECK_PENDING`, remains visible, and resumes automatically; approval and publication stay disabled until a verified duplicate check and conflict resolution complete. |

### D35: Typed web problem transport and domain outcomes

- Every expected non-success API response uses an RFC 9457-compatible `application/problem+json` envelope. Standard members are `type`, `title`, `status`, and a reviewed user-safe `detail`; opennosh extensions are a stable `code`, `schema_version`, `request_id`, and optional `retry_after`, `field_errors`, `latest_state`, and `recovery_actions`.
- Extension payloads are endpoint-specific generated types, not unrestricted dictionaries. A contribution conflict may return the newest safe capability document, while a validation failure may return addressable field errors. Responses never expose upstream exception text, secrets, private evidence, or internal stack context.
- The generated transport union is isolated behind per-domain adapters. Expected failures become exhaustive domain outcomes such as retryable, stale, partial, repair-required, conflict, or invalid-field states; React components render those outcomes without parsing messages.
- Network failures are a distinct client-side outcome with no invented HTTP status. Unknown codes, malformed problem bodies, and unexpected exceptions retain a safe reference and reach the nearest route error boundary; expected domain outcomes do not.
- Problem schemas are versioned with N/N-1 mapping fixtures. Adding an optional recovery field is backward-compatible; changing code meaning, field shape, or required handling requires a reviewed contract version.
- Contract tests cover every declared code, safe-message allowlisting, retry metadata, field addressing, latest-state repair, unknown-code fallback, malformed JSON, and correlation by `request_id`.

Progressive limits never affect whether data is considered true. They affect intake capacity only. Limit increases use explicit criteria such as completed accepted submissions without abuse findings, not a hidden composite score. Organized missions request time-bounded capacity through a steward decision with public scope and expiry. Network identifiers are minimized, rotated, access-controlled, and used only for abuse prevention.

OCR workers receive one evidence object and return a schema-bounded proposal. They cannot access account credentials, unrelated evidence, Git write paths, signing keys, or registry authority. Network egress is denied by default. Model packages are pinned and verified. Accuracy is benchmarked by label layout, script, locale, nutrient field, and confidence band; unsupported or low-confidence cases immediately use the manual path.

Anonymous fair-use limits do not require fingerprinting individuals. Hosted enforcement uses short-lived network buckets and endpoint cost, with documented limits and retry headers. Registered client credentials are hashed at rest, scoped to read or approved write capabilities, rotatable, revocable, and never embedded in public browser code. Bulk exports remain the preferred high-volume path and preserve release, license, and provenance metadata.

### Code Organization Rules

- Domain modules expose application services and typed contracts. No module reads or mutates another module’s database tables directly.
- `api/opennosh_api/foods/schemas.py` remains the API model source for food operations; `schemas/food-pack.schema.json` remains the portable-pack source; `web/lib/types.ts` food API types become generated output rather than a parallel manual contract.
- Generated artifacts carry generator version and input digest. CI regenerates and fails on diff, nondeterminism, or a breaking contract not accompanied by an approved version change.
- Pack-to-API and API-to-export transformations are named mappers with golden fixtures. They never drop attribution, license, provenance, canonical grams, original units, pack ID, record ID, or release version.
- Workflow states use explicit enums and transition functions. A route, worker, or UI component cannot assign state strings directly.
- Side-effect adapters are narrow interfaces with contract suites. Domain services do not import GitHub, object-storage, OCR-engine, signer, or search-vendor clients directly.
- Generic `utils`, catch-all service objects, and shared mutable dictionaries are prohibited. Shared code must name the domain concept it owns.
- Methods branching more than five times are split into state transitions, validators, or policy objects; a long match over a closed state enum is documented and exhaustively tested rather than hidden.
- Logs use typed event builders with allowlisted fields. Secrets, evidence bytes, raw OCR output, session tokens, and unrestricted user text cannot be passed to logging APIs.
- Every schema migration, contract change, and state transition includes forward compatibility, rollback behavior, and an ownership test.

### Over- and Under-Engineering Checks

- Keep one FastAPI codebase and PostgreSQL queue until measured contention justifies service extraction.
- Do not invent a universal schema that collapses operational API and portable-pack concerns.
- Do not hand-write four client implementations where OpenAPI generation and shared contract fixtures apply.
- Do not treat generated code as unreviewed code: pin generators, review contract diffs, scan packages, and test published artifacts.
- Do not compress publication, signing, or trust recovery into clever helpers. Explicit state and durable boundaries are required even when verbose.

### Test Reliability Rules

- Tests control time through an injected clock; they never wait for wall-clock expiry.
- Idempotency and concurrency tests use deterministic barriers, not probabilistic sleeps.
- External services are simulated by contract-faithful adapters in normal CI. Scheduled staging suites validate the real supported implementations.
- Randomized and property tests print and persist their seed on failure.
- Browser tests own isolated accounts, packs, and namespaces and clean them through supported APIs.
- No test depends on public network data, production Git repositories, global ordering, or another test’s side effects.
- Flaky tests are release failures. Quarantine requires an owner, issue, reason, and expiry, and cannot hide a P1 trust-path test.

### Shipping-Confidence Tests

- **Friday 2 a.m. test:** approve one evidence-backed contribution, kill the worker after every external side effect, restart, and prove exactly one published commit, signature, release, event, and index record.
- **Hostile QA test:** two devices, two stewards, duplicate webhooks, stale search, revoked role, expired session, and conflicting pack update all race without losing work or publishing invalid data.
- **Chaos test:** remove PostgreSQL, object storage, forge, registry, search, and online signing one at a time and in selected pairs; verify documented degraded behavior, alerts, recovery, RPO, and RTO.

### D40: Route-scoped font delivery budget

- Living Commons uses licensed WOFF2 variable-font subsets for Archivo, Source Sans 3, and IBM Plex Mono. Source files, subset commands, licenses, glyph/script manifests, and output hashes are versioned so a clean build is reproducible and auditable.
- Route-local `@font-face` definitions use stable `/fonts/v2/` URLs, and the localized public layout emits only the typed critical preloads. This explicit boundary replaces `next/font/local`, whose production manifest hoists preloads across independent roots; Tracker receives no Living Commons font class, preload, reference, or byte.
- The default Latin public route preloads only the above-the-fold Archivo display subset and Source Sans 3 body subset. IBM Plex Mono is non-critical and loads without preload. Additional script subsets are selected only for interface languages that need them; food-data locale alone never downloads another interface-font subset.
- All faces use reviewed metric-compatible fallbacks and a non-blocking display policy. The first render remains complete in fallback type, and font arrival cannot hide controls, alter reading order, or move the current task unexpectedly.
- Initial transferred font bytes for the default Latin public route are at most 160 KB. Deferred mono may bring the route total to at most 220 KB. A language needing another script records its measured subset budget and may replace, not automatically add to, the Latin payload when the page does not require both.
- Font-attributable cumulative layout shift is at most 0.02 in the representative mobile and desktop cold-load profiles. A font build, subset, or preload change fails CI when it exceeds transfer, request-count, unused-preload, or layout-shift budgets.
- Visual tests wait for production fonts to validate the intended composition; performance tests also capture cold fallback rendering and slow-font arrival. Both states must remain readable and usable.

### D41: CSS-first progressive motion budget

- Public headings, navigation, search, proof labels, accepted-event text, calls to action, and recovery controls are complete in server-rendered HTML and CSS before any motion controller loads. Motion is enhancement, never a route-ready or content-reveal dependency.
- Prefer CSS transforms, opacity, and accessible SVG. A small controller may coordinate intersection state, pause/resume, or state-bearing acceptance signals; it cannot recreate layout in JavaScript, poll for decorative updates, or run a general animation timeline.
- Motion-specific client JavaScript is at most 12 KB gzip. All design-delta client JavaScript beyond the shared Next.js framework is at most 45 KB gzip on the public homepage. Route chunk reports fail CI on regression unless an approved replacement removes equivalent cost.
- On the pinned representative low-power mobile profile, motion creates no main-thread task longer than 50 ms and the p95 frame time while visible motion runs is below 20 ms. Continuous ambient effects pause when hidden or offscreen and cap simultaneous active effects under a documented component budget.
- Optional motion code loads only after essential interaction readiness and only for eligible preferences. Reduced-motion and data-saver paths do not download optional motion chunks; low-power mode and runtime budget breach disable decoration before task feedback or state visibility.
- Field gates at the 75th percentile, segmented by mobile and desktop, are LCP at most 2.5 seconds, INP at most 200 ms, and CLS at most 0.1. Lab gates record first-load JS, parse/evaluation, total blocking time, long tasks, frame times, memory high-water mark, and offscreen CPU.
- Performance tests cover cold and warm loads, no-JavaScript content, reduced motion, data saver, background/foreground transitions, long pages, multiple accepted events, and contribution-stage navigation. Synthetic passing cannot override a failing field budget without a documented measurement-quality exception.

### D42: Bounded precomputed homepage proof snapshot

- A rebuildable public projection materializes the verified record count, release identity, freshness, `accepted_count_in_window`, and the latest four accepted events at or before the resolved release. Four events match the approved large-row composition; the aggregate communicates activity volume without sending a growing list.
- Projection input is verified signed receipts and accepted events. The projection stores its source release digest, event checkpoint, schema version, activity cutoff, and build time so reconciliation can prove or rebuild it; it is never a canonical trust source.
- A homepage request resolves the versioned snapshot through one bounded cache/projection read. It does not scan the accepted-event table, join evidence, or fetch event details per row. Event summaries are preformatted from allowlisted public fields and contain no contributor location or private evidence.
- The uncompressed `PublicCommonsSnapshot` response is at most 24 KB. Each event has bounded identifiers, timestamp, event type, broad food locale, text summary, record link, pack/release identity, and verification reference; oversize source text is summarized or rejected during projection.
- The snapshot uses a five-minute `as_of` bucket for the rolling 24-hour window. Publication and projection completion invalidate the relevant snapshot; edge revalidation refreshes the whole document atomically. Clients do not poll or stream homepage activity.
- ETag and cache identity include schema, release digest, event checkpoint, activity cutoff, and `as_of` bucket. A stale fallback keeps the last verified four events and aggregate with visible age; it never merges a fresh count with old rows.
- A later paginated activity route may expose deeper history through snapshot-bound cursors. It is a separate read contract and cannot increase the homepage event or payload budget.

### D43: Local-immediate, coalesced contribution autosave

- Eligible non-sensitive field edits persist to the versioned local draft immediately. The UI may announce `Saved on this device` only after that write succeeds; `Synced` appears only after the server acknowledges the matching or newer draft version.
- Server synchronization begins after 750 ms without a new eligible edit, with a five-second maximum wait. Stage transition and an explicit retry request flush pending fields; navigation and page close rely on the durable local copy rather than blocking unload or claiming a last-second network save succeeded.
- At most one autosave mutation is in flight per draft. New edits coalesce by field behind it and send after acknowledgement against the newest known server version. The client does not abort an acknowledged-or-unknown mutation to create concurrency; disconnect after send is repaired by idempotency and capability reload.
- Each patch carries the expected draft version, stable client operation ID/idempotency key, changed field values, and the base value/version needed for the approved field-conflict policy. It never resends evidence bytes or the entire draft for a text-field change.
- Offline state stores only the newest pending safe value and base version per field, not an unbounded keystroke/event log. Evidence, secrets, and fields excluded by the persistence policy never enter this queue. Queue size, age, and schema version are bounded and visible to repair logic.
- Save states are `saved_on_device`, `sync_scheduled`, `syncing`, `synced`, `offline`, `conflict`, and `repair_required`. Stale or out-of-order responses cannot downgrade a newer visible state; conflict and repair responses preserve local work and the latest server capability document.
- Cross-tab drafts carry writer-qualified monotonic storage revisions and merge latest safe values by field. Same-field conflicts retain the original base, block automatic retry and submission, and require an explicit keep-device or use-server resolution. Malformed persisted operations fail into repair rather than reaching the network.
- Idempotency operations are retained for eight days, exceeding the seven-day client retry window, then pruned per draft. The PATCH route applies per-draft and aggregate per-owner mutation limits of 120 and 240 per minute by default.
- Tests use an injected clock and deterministic request barriers for rapid typing, slow response, disconnect-before/after commit, two tabs, two devices, stage change, visibility change, session expiry, schema upgrade, retry, and conflict. Metrics record patches per active editing minute, coalescing ratio, payload size, acknowledgement latency, conflict rate, and offline queue age without field values.

- Roles: unique `(actor_id, scope_type, scope_id, role)` with revocation lookup.
- Reviews: `(state, acknowledged_at, submitted_at)` for median, p90, and aging SLOs.

### Memory, Payload, and Connection Rules

- APIs and workers stream pack files, exports, and evidence; they never load an unbounded corpus or archive into memory.
- Every job payload contains identifiers and versions, not binary evidence or entire packs.
- Pack manifests declare counts and sizes that are checked before fetch and again while streaming; compressed and decoded limits both apply.
- Search pages use stable cursor pagination and a bounded page size. Facet counts are bounded or precomputed.
- Each process role has its own PostgreSQL pool budget; total configured pools must remain below the database connection ceiling with headroom for migrations and recovery.
- OCR model memory belongs only to evidence workers. Web and publication processes never import or initialize models.
- Load tests report p50, p95, p99, error rate, connection saturation, job age, index lag, and memory high-water mark, not averages alone.

### Search Extraction Gate

A versioned benchmark corpus includes short and long names, multiple scripts, misspellings, locale variants, duplicate clusters, conflicting packs, missing nutrients, and worst-case filters. The dedicated-engine spike begins only if PostgreSQL misses the latency targets at the planned two-year corpus size, relevance falls below the judged baseline, indexing cannot complete inside the release SLO, or operational load threatens write-side PostgreSQL. Extraction is a projection replacement, not a data migration.

### Cache Invariants

- Immutable responses include content digest, pack ID, release version, schema version, license, provenance reference, and `Cache-Control: immutable` semantics.
- A latest alias never caches longer than its published policy and always returns the resolved immutable URL or equivalent release metadata.
- Alias invalidation occurs only after publication reaches `PUBLISHED`; an index or purge failure cannot expose an unverified release.
- `stale-if-error` serves only a previously verified response and adds machine-readable and visible stale age. It never converts not-found or license/quarantine changes into stale success.
- Quarantine revokes the latest alias immediately and blocks new installs. Previously downloaded immutable artifacts remain identifiable, but hosted access displays the quarantine decision.
- Search cursors encode the release-set snapshot and expire cleanly when the server no longer retains that projection.
- CDN logs exclude query text, evidence references, tracker paths, credentials, and full IP retention beyond the documented abuse window.

### Alerts and Runbooks

- **Critical:** signature bypass or invalid signed publication, unauthorized privileged mutation, irreversible published-evidence loss, incompatible-license combined export, malicious trust recovery, or privacy-threshold leak. Page immediately, quarantine affected scope, preserve evidence, and publish incident status.
- **High:** publication or projection SLO breach, reconciliation divergence, database write outage, evidence integrity mismatch, restore failure, or compromised online key. Page owning operator and enter documented degraded mode.
- **Medium:** review backlog breach, pack staleness, search latency budget, OCR failure surge, client abuse, storage capacity, or expiring trust metadata. Create owned incident with deadline before promotion.
- Every alert names the affected user surface, safe automated action, operator, escalation, rollback boundary, and verification query. Alerts without a tested runbook cannot ship.
- Synthetic checks use dedicated marked traffic and are excluded from adoption metrics.

### Public Status Contract

- Components report `operational`, `degraded`, `outage`, `maintenance`, or `unknown`. Operational requires a successful monitor observation newer than the component's versioned freshness window; missing, stale, future, malformed, or unsuccessful operational evidence is unknown.
- Search staleness, contribution pause, evidence-processing delay, publication backlog, registry quarantine, API rate incident, download failure, and tracker outage remain separate components.
- Inline product notices consume the same status source and link to the incident. The status page never contradicts the affected screen.
- Security incidents publish user impact and safe actions promptly while exploit details, credentials, and active containment data remain restricted.
- Recovery closes only after the verification query and synthetic user journey pass, not merely when a process restarts.
- Incident transitions are append-only and version-aware. Resolution requires a verified UTC recovery observation and lowercase SHA-256 evidence digest.
- Self-hosted deployments receive the schema, local page, and health endpoint; remote publication or subscription is optional.

### Rollout Invariants

- A flag controls routing and side effects, not the existence of canonical accepted data. Turning a flag off cannot delete or rewrite releases.
- Shadow jobs use separate namespaces and cannot emit accepted events, notifications, mission progress, or public impact.
- Cohort membership is server-side and auditable. Client parameters cannot self-enroll into privileged features.
- Old and new application versions may overlap during deployment. Every database, job, event, and API change defines the mixed-version window.
- Worker rollback never abandons unknown job types. Older workers leave unsupported jobs unclaimed while the compatible version remains available.
- Post-deploy checks run at five minutes, one hour, and after the first full reconciliation cycle. A passing process health check alone cannot close rollout.
- Each flag has an owner, creation reason, rollout stage, dependencies, expiry, and tested off-path. Expired flags fail CI until removed or explicitly renewed.

### Self-Hosted Upgrade Contract

- Release fixtures preserve the previous major’s database, jobs, packs, evidence metadata, keys, configuration, and tracker data. CI upgrades each fixture and runs public, contribution, publication, federation, and tracker smoke tests.
- Preflight is read-only. It names every blocker, safe remediation, expected downtime, backup requirement, and rollback boundary before requesting confirmation.
- Upgrade never rotates trust roots, deletes evidence, rewrites Git, changes pack license, or enables remote telemetry implicitly.
- Mixed-version support lasts through the documented rolling-deploy window. Job and event consumers ignore or park unsupported future types safely.
- A signed compatibility matrix covers server, web, database, pack spec, OpenAPI, SDK/CLI/MCP, storage adapter, OCR model, and signer metadata versions.
- Sequential upgrade documentation remains downloadable with the release artifacts so an air-gapped operator does not depend on the hosted site.
- Rollback restores application binaries and feature state first. Schema rollback occurs only where explicitly proven safe; otherwise the previous app must tolerate the additive schema.

### Hero Proof Counter Contract

The open-ring hero may display the current verified public-record count as evidence of the commons, not as decorative motion.

- Source the count from the signed published-release manifest or its independently verified immutable projection.
- Label the value with its meaning and verification boundary, for example `18,429 verified records | release 2026.08.22`.
- Update the count only after the corresponding release reaches `PUBLISHED`; search indexing or a pending contribution never changes it.
- Never count upward on a timer, interpolate between releases, add random increments, or animate digits merely to imply activity.
- If the latest check fails, retain the last verified value and show its release or stale age. If no verified count exists, preserve the open-ring composition without a number and keep search available.
- The footer and any repeated count resolve the same release snapshot. Different sections cannot display different totals.
- Prototype counts carry a visible `ILLUSTRATIVE DATA` label or are removed before public use.

### Public commons snapshot contract

The homepage resolves one server-side `PublicCommonsSnapshot` and passes that immutable response through the render tree. Hero, footer, accepted activity, and their freshness messages cannot fetch competing snapshots independently.

- The response includes a schema version, snapshot identifier, `as_of` time, resolved release version and manifest digest, verified record count, release publication time, activity window, `accepted_count_in_window`, the latest four accepted events, most recent verified record for the quiet state, component freshness, and typed partial or unavailable reasons. D42 owns the projection, payload, cache, and refresh budgets.
- Resolve and verify the signed latest-release pointer once. Accepted activity is bounded to receipts at or before that release and to the declared rolling window; a projection can lag and mark the snapshot partial, but it cannot introduce an event from a newer unresolved release.
- The overview response is a rebuildable read model, not a new trust root. It carries signed manifest and publication-receipt digests so clients and operators can trace every proof signal to canonical artifacts.
- The server render fetches or constructs the snapshot once and supplies it to the hero, activity feed, repeated count, and footer. Client hydration cannot refetch one section onto a different release silently.
- Cache keys and ETags bind the release digest, activity cutoff, snapshot schema, and bounded `as_of` bucket. On dependency failure, serve only the last verified snapshot with a visible stale age; if none exists, omit the number, mark activity unavailable, and keep search usable.
- Contract, integration, cache, restore, and browser tests cover release changes during render, activity projection lag, missing receipt projection, invalid latest pointer, cache revalidation failure, quiet-window aging, PostgreSQL outage, and first-run absence.


### Motion and Accessibility Contract

- The initial document contains complete headings, navigation, search, calls to action, status, and explanatory text before motion code loads.

### Contribution Stage Contract

| Stage | Primary question | Completion evidence | Blocking states |
|-------|------------------|---------------------|-----------------|
| Evidence | What source supports this food? | Safe image/reference, rights acknowledgement, hash, source type | Unsafe upload, unavailable durable draft store, missing required source |
| Details | What does the source actually say? | Confirmed identity, portions, nutrients, ingredients, locale; original and canonical units | Invalid ranges/types, unresolved local/server field conflict |
| Duplicates | Does this already exist? | Verified projection check and resolved equivalence candidates | `DUPLICATE_CHECK_PENDING`, unresolved candidate |
| Provenance | Who produced this claim and under what license? | Pack, source, date, attribution, license, contributor identity policy | Missing/incompatible license, unsupported pack target |
| Review & Submit | Is this exact contribution ready for public review? | Versioned summary, evidence links, validation result, idempotency key | Any previous-stage gap, expired authorization, changed schema |

### Contribution Chapter Mapping

The contribution journey has three narrative chapters containing five operational stages:

| Chapter | Operational stages | Promise to the contributor |
|---------|--------------------|----------------------------|
| 1. Begin the record | 1. Evidence, 2. Details | Start with the source and describe only what it supports. |
| 2. Verify the claim | 3. Duplicates, 4. Provenance | Check whether the food already exists and make its origin, pack, attribution, and license explicit. |
| 3. Send to the commons | 5. Review & Submit | Inspect the exact public proposal, understand review and attribution, then submit once. |

- URLs, draft state, validation ownership, resume links, and progress announcements use the five operational stages.
- Chapter names provide orientation and humane language. They are not separate saved states and never hide which operational stage is blocked.
- Desktop step rails group stages under their chapter. Mobile progress shows both the chapter and `Step N of 5`, for example `Verify the claim | Step 3 of 5 | Duplicates`.
- Completing a chapter does not imply acceptance. Only verified publication completes the contribution-to-commons loop.

### Contribution stage authority contract

The URL requests a contribution view; it never grants workflow progress. The server draft is authoritative after account handoff.

- The five operational stages are one versioned enum shared by API schemas and generated transport types. Narrative chapters remain presentation metadata and never appear as authorization or persistence states.
- A draft capability response includes `workflow_version`, `draft_version`, review state, completed stages, accessible stages, blockers keyed to owning stage and field, saved time, and the next safe action. Every successful mutation returns the refreshed capability document.
- Local anonymous drafting uses the same versioned pure transition rules for non-sensitive fields. After sign-in handoff, the server version wins; field-level conflicts remain explicit and evidence follows its stricter persistence rules.
- A localized route such as `/en/contribute/{draft_id}/{stage}` identifies the requested view. Loading an inaccessible or unknown stage returns a typed repair result and the capability document; the UI explains the blocker and moves to the nearest safe stage without claiming that work was lost.
- Back, forward, step-rail, and resume navigation do not mutate workflow state. Editing an earlier stage may invalidate downstream completion, which the next server response exposes explicitly.
- Mutations carry the expected draft version and an idempotency key. Autosave scheduling, coalescing, local status, and serialized patches follow D43. Version conflict, role change, schema change, or review lock returns a typed non-success response with the latest safe capability state.
- Submission revalidates every stage, evidence reference, duplicate result, provenance field, license, actor authorization, and draft version transactionally. Client completion flags cannot authorize submission or publication.
- Contract, state-machine, integration, and browser tests cover forged later-stage URLs, stale tabs, concurrent edits, backward edits that invalidate later stages, session expiry, schema upgrades, duplicate submit, review lock, and safe resume.


### D37: Exhaustive contribution-stage presentation registry

- One frontend registry is keyed exhaustively by the generated five-stage enum. Each entry owns its stable route slug, order, narrative chapter, heading and description translation keys, validation-summary anchor, safe analytics identifier, and previous/next presentation relationship.
- Desktop rails, compact progress, mobile step lists, breadcrumbs, route builders, resume links, error summaries, and tests derive stage presentation from this registry. Components may filter by server capability, but cannot define independent stage arrays or infer authorization from registry order.
- The server capability document remains authoritative for completed, accessible, blocked, and next-safe stages. The registry contains no completion rules, validation logic, permissions, or mutable draft state.
- Compile-time exhaustiveness fails when the generated enum changes without a presentation entry. Unit tests reject duplicate order, slug, analytics identifier, heading anchor, or missing translation keys; route and browser tests prove every stage resolves consistently in each supported interface language.
- Chapter metadata remains frontend presentation only. It groups the five operational stages and never becomes a persisted workflow state or API authorization concept.

### Contribution Responsive Contract

- **Wide desktop, 1200 px and above:** Use a persistent left step rail beside the primary task. Evidence and structured fields may appear side by side only when each retains a readable width and logical source order.
- **Tablet and compact desktop, 768-1199 px:** Move progress above the task, keep the current stage and saved state visible, and present evidence before the fields it supports. Do not squeeze the desktop comparison layout.
- **Mobile, below 768 px:** Show a compact progress header with `Step N of 5`, stage name, and saved or blocked state. `View all steps` expands a semantic ordered list in place and returns focus to its trigger when closed.

### Emotional and Information Hierarchy

1. **Invitation:** The public site communicates that food data is shared infrastructure and offers immediate search.
2. **Trust:** A record reveals provenance, evidence state, variants, license, and history before asking for participation.

### Food Record First-Viewport Hierarchy

Every food record uses utility with visible trust. The initial viewport answers the nutrition question quickly while proving that the answer belongs to a sourced, versioned record.

## Program Scope Confirmation

The assembled opennosh vision is confirmed as one phased program with six accepted expansions:

1. Federated Pack Network distributes ownership.
2. Evidence-First Capture creates trustworthy claims.
3. Commons Missions organize useful participation.
4. Public Stewardship and Dispute Resolution govern conflicts.
5. Developer Distribution Kit spreads adoption.
6. Public Reuse and Impact Map closes the value loop.

These are program scope, not a commitment to launch every capability simultaneously. Delivery remains governed by the release trains, promotion gates, feature flags, and rollback contracts defined above.

## Engineering Review Scope

Decision D1 narrows the first implementation and engineering-review unit without cutting the approved program.

### First vertical trust loop

- Public homepage, anonymous search, food detail, provenance, license, and stable tracker handoff.
- Canonical API and pack contracts with generated web/client types and lossless mapping tests.
- PostgreSQL jobs, transactional outbox, idempotency, typed failures, and reconciliation required by the loop.
- Evidence capture with secure storage, safe rewrite, manual entry, optional first-party OCR, and durable publication acknowledgement.
- Contribution drafts, duplicate checking, steward review, disputes required for the pilot, and explicit publication states.
- One opennosh-operated signed pack, one forge adapter, one registry/release path, and one reference reuse client.
- Observability, recovery, security, accessibility, performance, and deployment gates required to operate this loop safely.

### Later release trains

Multi-maintainer federation enrollment and cross-pack breadth, Commons Missions, the remaining SDK/CLI/MCP/embed surfaces, the full reuse registry, public impact mapping, and ecosystem-scale governance remain accepted program scope. This first unit defines only the contracts needed to avoid blocking them; their detailed implementation review occurs when their release train begins.

The first unit is complete only when a real evidence-backed contribution can move through review and durable signed publication exactly once, appear in anonymous search with provenance, survive the documented failure drills, and be consumed by the reference client.

### Design-delta delivery slices

The six design-review tasks remain part of the first vertical trust loop, but they do not ship as one coupled frontend release. Backend prerequisites may land disabled or in shadow mode; each visible slice has its own feature flag, acceptance evidence, and rollback path.

1. **Foundation shell:** Move the existing tracker and its effective styles behavior-neutrally to `/tracker`, isolate tracker and public route layouts, commit the canonical design system and assets, and add the task-first public shell. Root-route activation waits for tracker parity, navigation, focus, responsive, and flag-off tests.
2. **Trustworthy public reads:** Add generated transport boundaries, immutable verified read artifacts, the food-record trust hierarchy, the signed-release count, and complete accepted-activity states. A surface stays hidden until its real source, stale behavior, and no-data behavior verify; illustrative data never enters the production path.
3. **Contribution and completion:** Add the three-chapter, five-stage contribution UI only after draft, evidence, duplicate, review, receipt, and publication contracts exist. The slice exits only when the real browser-to-signed-receipt journey passes and submission cannot impersonate publication.

Slices merge incrementally and may overlap in engineering work, but production exposure proceeds in this order. A later slice cannot widen the rollback or data-integrity boundary of an earlier one.

## Engineering Review Decisions

### D2: Artifact-backed immutable read plane

The vertical trust loop includes an independently serveable read plane derived from verified publication artifacts:

```text
REVIEWED CONTRIBUTION
        │
        ▼
Git commit → signed pack release → publication verification
                                      │
                         ┌────────────┴─────────────┐
                         ▼                          ▼
              PostgreSQL/search projection   Immutable read snapshot
                         │                    record JSON · provenance HTML
                         │                    pack download · signed manifest
                         ▼                          │
              Dynamic search and latest            ▼
              contribution activity        Object storage / CDN
                         │                          │
                         └────────────┬─────────────┘
                                      ▼
                          Public food pages and API
```

- Publication writes content-addressed record JSON, provenance HTML or equivalent semantic payload, signed pack downloads, and a signed release manifest to the independently durable artifact store.
- A short-lived latest pointer resolves to one immutable verified release and changes only after publication reaches `PUBLISHED`.
- Immutable record and provenance URLs remain available without PostgreSQL. The public food-detail route can resolve the signed latest pointer or a pinned version directly from the artifact read adapter.
- Search, accounts, drafts, review, and contribution remain PostgreSQL-backed. During database failure they expose the documented degraded or paused states instead of pretending to work.
- Cache and CDN invalidation failures may serve the previous verified release with a visible stale age; they can never expose an unverified release.
- Tests remove PostgreSQL and FastAPI dependencies independently and verify that food detail, provenance, immutable API records, and downloads remain correct while dynamic features degrade honestly.


### D3: Steward-authorized protected automatic merge

- A scoped steward approval is the only routine human governance authorization for the vertical trust loop.
- The publication outbox records the approving steward, reviewed payload digest, expected base commit, required checks, forge target, and idempotency key.
- A narrowly scoped forge application creates the contribution branch and pull request, then idempotently arms protected squash auto-merge while the independently sourced governance attestation is still blocking. The worker observes an existing auto-merge request on recovery. A short per-pack transaction serializes the final authority reload with governance withdrawal and commits immutable authority bound to the exact head and payload; that commit is the merge-authorization linearization point. The database connection is released before the independent attester emits the protected check and GitHub completes the already-armed merge. The application cannot bypass branch protection or required validation.
- Required checks verify schema, provenance, license, evidence manifest, payload digest, contribution authorization, and self-review prohibition.
- The pull request merge is a mechanical completion of the steward decision, not a hidden second review queue.
- A maintainer may pause or reject protected merge only through an audited intervention that records the reason and returns the contribution to an explicit retrying, blocked, or changes-requested state.
- The contributor cannot approve their own contribution. Role scope and recusal are rechecked when approval is recorded and again before merge.
- Publication observes the merged commit, proves its tree matches the approved payload, and only then proceeds to signing and durable publication.
- Forge adapters implement equivalent protected-check semantics where available. A local-Git adapter requires the same authorization and validation evidence before updating its canonical branch.


### D4: Typed evidence manifests and class-specific durability

Manual entry and OCR describe data-entry methods. They are not evidence classes and do not change the proof required for publication.

| Evidence class | Required canonical fields | Publication durability | Public verification state |
|----------------|---------------------------|------------------------|---------------------------|
| Sanitized media | Content digest, safe format, capture/source description, rights acknowledgement, redaction state, storage reference | Immutable independently durable sanitized copy plus verified digest | `evidence_preserved` while accessible; tombstoned with reason after governed removal |
| Versioned public dataset | Dataset ID, release/version, record ID, publisher, license, source URI, canonical record digest | Independently durable dataset release or record snapshot where licensing permits, plus signed manifest reference | `source_verified` with preserved release identity |
| Public document or web citation | Canonical URI, publisher, title, observed time, observed digest, license/rights state | Archived copy when permitted; otherwise immutable citation manifest and observed digest | `reference_preserved` or honest `reference_only` when bytes cannot be archived |
| Maintainer attestation | Identified authority, scope, signed statement, time, license, supporting reference | Signed attestation and manifest preserved with the release | `attested`, never visually equivalent to preserved primary evidence |

- Manual transcription must select one evidence class and capture its required fields. A claim with no supporting evidence remains a draft or explicitly unverified proposal and cannot enter the verified community pack.
- OCR proposals inherit the uploaded media evidence manifest and never create independent evidence.
- The publication invariant evaluates the durability policy attached to each evidence class. It does not blindly require image bytes when the source is a dataset, document, or signed attestation.
- If rights prevent byte preservation, the UI and API expose `reference_only`; they never imply that opennosh retained or can reproduce the source.
- Evidence removal preserves the manifest, decision history, digest, and governed tombstone without claiming continued access to removed bytes.
- Contract tests cover every evidence class, missing required fields, rights-restricted archival, source disappearance, digest mismatch, tombstoning, and trust-label rendering.


### D5: PgQueuer for delivery, opennosh for publication correctness

- opennosh defines a narrow `JobQueue` port for enqueue, lane, run-after, priority, deduplication key, attempt context, cancellation, and health.
- PgQueuer is the first PostgreSQL adapter, pinned only after a bounded spike verifies Python and PostgreSQL compatibility, transactional enqueue, crash recovery, retry timing, priority fairness, graceful shutdown, schema upgrades, namespacing, metrics, and supported licensing.
- Queue payloads contain typed identifiers, schema versions, trace context, and idempotency keys. They never contain media bytes, unrestricted records, secrets, or authority decisions.
- opennosh retains its own `publication_intent`, `publication_step`, durable acknowledgement, and accepted-event tables. A queue job only wakes the orchestrator; queue completion never proves publication completion.
- The approval transaction writes the reviewed decision, publication intent, and queue wake-up atomically. A rollback creates none of them.
- Every handler is safe under at-least-once delivery and verifies external state before side effects. No plan or test assumes the queue provides exactly-once execution.
- PgQueuer migrations are explicit, namespaced, reviewed, backed up, and included in N/N-1 upgrade fixtures. The adapter contract allows replacement without changing domain states.
- If the spike fails a required integrity or operational test, implementation stops for an explicit queue-adapter decision rather than silently falling back to a custom partial queue.

### D6: Signed publication receipt as the canonical accepted event

- `PUBLISHED` is proven by a signed, versioned publication receipt, not only by a PostgreSQL row.
- The receipt binds schema version, pack and record IDs, reviewed decision ID and actor scope, approved payload digest, base and merged commit/tree, evidence-manifest digests and class-specific durable acknowledgements, signed release metadata digest and version, registry acknowledgement/result, artifact read-snapshot digests, publication timestamp, publisher/adapter identity, and an idempotency-key hash.
- Create the receipt only after every required external state has been verified. The publication role signs it, copies it to the registry and an independent immutable artifact store, then verifies those copies before PostgreSQL records `PUBLISHED`.
- Rebuild PostgreSQL accepted events and the mission, impact, and activity projections from verified receipts after operational database loss.
- Reconciliation enumerates receipts and external artifacts, recreates missing rows idempotently, and never repeats a side effect whose receipt and external state already verify.
- If the receipt is missing or invalid, the candidate remains non-published, retrying, or quarantined according to the verified external state.
- Corrections and revocations create new signed receipts that link to the prior receipt. Published receipts are never rewritten.
- Test crash boundaries before and after receipt creation, one unavailable receipt destination, receipt tampering, restoration to a pre-publication database snapshot, duplicate replay, and late registry acknowledgement.

### D7: Two-checkpoint tracker route migration

- First create `/tracker` as a behavior-neutral route that renders the existing tracker without redesigning its state or API behavior.
- Centralize canonical route definitions and update tracker navigation, tests, PWA metadata, documentation, and release notes to use `/tracker`.
- During the compatibility checkpoint, keep `/` serving the tracker with visible, keyboard-accessible, dismissible handoff guidance. Do not use an authentication-dependent or session-dependent redirect.
- Prove parity with the existing tracker regression suite plus explicit root compatibility and `/tracker` route tests before changing the root experience.
- In a separate checkpoint, place the public commons at `/` behind its own feature flag. Keep a prominent tracker link and the approved time-bounded migration guidance.
- A public-homepage rollback changes only the root feature flag or public route. It never removes or rewrites the verified `/tracker` implementation.
- Do not mix tracker behavior refactors, navigation redesign, or generated-client adoption into the structural route-migration checkpoint.

### D8: Generated transport types behind stable UI models

- Store deterministic, immutable generated OpenAPI output under `web/lib/generated/`; generated files are never edited by hand.
- Only the API transport and adapter layer may import generated response or request types. React components, hooks, feature state, and presentation tests import stable handwritten feature/domain models.
- Map every transport payload into a UI model at the adapter boundary. Mappings are exhaustive for identity, provenance, licensing, units, schema/version fields, and explicit nullable states.
- Keep transport-to-domain mapping functions small, pure, and colocated with the owning API adapter. Do not create a second universal food schema.
- Commit pinned generator configuration and generated output. CI regenerates it and fails on a diff, runs an OpenAPI breaking-change gate, and reviews dependency and generated-code changes.
- Golden contract fixtures cover API-to-UI mappings, including required provenance fields, unknown enum values, nullable additions, and N/N-1 response fixtures.
- Published JavaScript and Python clients may expose generated transport models through their documented public APIs, but the opennosh web UI does not import generator internals directly.

### D9: Incremental domain model split with one explicit registry

- Keep one SQLAlchemy declarative `Base` and one `MetaData` graph for the modular monolith.
- Move existing models incrementally from `models/tables.py` into their owning domain modules. A structural move must produce no database schema change and no Alembic migration.
- Add an explicit model registry that imports every owning model module for mapper registration and exposes the complete metadata to Alembic, startup validation, and test fixtures.
- Each table has exactly one declared owner. Domain services import their own models and call another domain through its application service or typed contract rather than reading or mutating its ORM model.
- Cross-domain database references use stable identifier types and string foreign-key targets. Avoid ORM relationships that make one domain traverse another domain's aggregate implicitly.
- Keep temporary compatibility re-exports from `opennosh_api.models` while call sites move, mark them for removal, and prohibit new imports through that compatibility surface.
- Registry tests assert the complete expected table set, one owner per table, deterministic import registration, and a clean Alembic schema check after every model relocation.
- New movement-platform tables begin in their owning domain modules and register through the same registry; they are not added to the legacy catch-all file.

### D10: Explicit process composition roots and a separate migration job

- Provide dedicated entrypoints for the FastAPI web process, publication worker, evidence worker, projection worker, reconciler, and scheduler.
- Each composition root constructs only its owned adapters, PostgreSQL pool, queue lanes, telemetry, health checks, concurrency controls, and shutdown hooks. Importing a role must not initialize another role's infrastructure.
- Share domain services, typed settings, model registry, and adapter protocols within the modular monolith. Do not create network boundaries between these roles.
- Give every role an explicit packaged command, deployment identity, least-privilege credentials, liveness contract, readiness contract, drain behavior, and pool/concurrency budget.
- Run Alembic once as a distinct deployment job before compatible application rollout. Web and worker container commands never run migrations automatically on startup.
- Local development may provide one convenience supervisor that launches all roles, but production role processes remain separate and independently restartable.
- Startup architecture tests assert that each role registers only its allowed queue lanes and adapters, respects the global PostgreSQL connection budget, and shuts down without abandoning or acknowledging leased work.
- N/N-1 deployment tests prove old roles leave unknown job types unclaimed and new roles tolerate the additive schema during the rollback window.

### D11: Deterministic publication planner, effect executor, and reducer

- Model publication as a versioned durable snapshot processed by three explicit layers: a pure next-action planner, a narrow external-effect executor, and a transactional result reducer.
- The planner receives the persisted snapshot plus verified external observations and returns exactly one typed outcome: transition, effect intent, wait condition, quarantine, terminal failure, or no-op.
- Transition and planning code performs no network, filesystem, clock, random, queue, or database operations. All nondeterministic inputs are explicit values.
- An executor handles one bounded effect intent through one adapter using a deterministic idempotency key derived from publication identity, workflow version, step, destination, and approved payload digest.
- After the effect, independently verify the external state. A reducer transaction stores the observation/result, durable acknowledgement, and next workflow version before another effect may begin.
- Each lease performs at most one external-effect boundary before checkpointing and acknowledging its wake-up job. Lease loss stops execution before planning the next effect.
- Use exhaustive transition-table tests, property-based invariants, adapter contract tests, and crash injection before and after every executor/reducer boundary.
- Keep this engine specific to the explicit publication protocol. Do not introduce a generic workflow DSL or framework.

### D12: Shared deterministic workflow testkit

- Create one reusable testkit for contribution, evidence, review, publication, receipt, and projection workflows.
- Inject the clock, identifier generator, idempotency-key source, adapter results, and scheduler decisions. Tests do not wait for wall-clock expiry or use sleeps as concurrency assertions.
- Every registered publication step exposes named failpoints before intent execution, after the external effect, before verification, after verification, before reducer commit, and after reducer commit.
- Contract-faithful fake forge, object-storage, OCR, signer, registry, search, and queue adapters persist inspectable external state independently of the worker instance.
- The harness can terminate and recreate a worker while preserving PostgreSQL plus fake external state, replay duplicate jobs and webhooks, expire leases deterministically, and restore a selected database snapshot.
- Generate the crash/retry scenario matrix from the versioned publication-step registry so adding a step without failure scenarios fails CI.
- Assert global invariants after every scenario: no unsupported state transition, no duplicate governed effect, at most one canonical accepted release, complete required evidence, verified durable copies, one valid receipt lineage, and no false `PUBLISHED`.
- Run the deterministic matrix in normal CI. Scheduled staging drills rerun the critical subset against supported real forge, storage, signing, registry, and restore implementations.
- Replace existing synchronization sleeps with explicit events/barriers as affected suites are touched; the trust-path suites accept no probabilistic synchronization.

### D13: Fast UI journeys plus real vertical browser acceptance

- Maintain two explicitly named Playwright lanes with different responsibilities and failure ownership.
- The UI-journey lane intercepts requests only with contract-valid generated fixtures and covers loading, empty, error, partial, stale, success, responsive, reduced-motion, keyboard, screen-reader, and focus behavior. It runs broadly on every pull request.
- The vertical-acceptance lane runs real Next.js, same-origin proxy, FastAPI, PostgreSQL, queue workers, and contract-faithful external adapters. It does not intercept opennosh API traffic.
- Use versioned supported fixture commands and per-test accounts, packs, evidence namespaces, and adapter namespaces. Do not mutate the database directly during an acceptance journey.
- Exercise critical visitor, contributor, steward, and tracker actions through the browser. Verify the final result independently through the signed publication receipt, immutable public artifact, provenance surface, and reference client.
- Run one critical vertical trust-loop smoke journey on pull requests. Run the wider role, browser, locale, mobile, interruption, and accessibility matrix on schedule.
- Report UI-journey and vertical-acceptance failures separately so a presentation failure is distinguishable from a contract, backend, worker, or publication failure.
- Existing API-mocked Playwright tests become UI-journey tests; they are not described as end-to-end trust-loop proof.

### D14: Risk-tiered required trust-path gates

- Every pull request runs lint, strict types, deterministic generation, breaking-contract checks, unit/property tests, authorization tests, PostgreSQL integration, fast UI journeys, and one critical real-stack browser trust loop.
- Trust-protocol changes run the complete deterministic transition and rescue matrix affected by the changed step registry. Trust state machines and security-policy modules require 100 percent transition, rescue-outcome, and policy-branch coverage.
- General changed production code maintains a high changed-code coverage threshold and cannot reduce repository coverage without an explicit reviewed exception. Line coverage alone never substitutes for state, property, mutation, or failure-path proof.
- A trust-path test that passes only on retry still fails the required gate. A separate diagnostic rerun may capture traces, screenshots, logs, and seeds without changing the result.
- Before release, run the full role, browser, mobile, locale, accessibility, package-install, N/N-1 upgrade, rollback, signed-receipt reconstruction, and supported self-host configuration suites.
- Scheduled staging exercises real supported forge, object-storage, signer, registry, and OCR integrations plus backup restore, paired outages, key loss/recovery, and representative load.
- Every gate has an owner, maximum runtime budget, artifact-retention policy, and documented failure triage. Quarantine requires an issue, owner, reason, expiry, and cannot bypass a P1 trust-path or security check.
- CI reports the exact untested transition, rescue outcome, contract, browser role, or recovery drill rather than only a global coverage percentage.

### D15: Signed snapshot-bound keyset search cursors

- Replace public search offsets with opaque signed keyset cursors for the movement-platform search contract.
- A cursor binds cursor schema version, retained projection or release-set snapshot ID, normalized query/filter fingerprint, ranking version, last rank plus deterministic tie-break tuple, page size policy, and expiry.
- Do not place raw query text, credentials, contributor identity, or private filters in cursor payloads or logs.
- The next page runs strictly after the encoded tuple against the same retained projection snapshot. Publication and atomic projection swaps cannot change membership or ordering within an active pagination journey.
- Retain projection snapshots for a documented cursor lifetime. When a snapshot or cursor version expires, return a typed restart response with the current first-page link rather than silently mixing release sets.
- Cursor signatures rotate through a versioned key ring with N/N-1 verification during the compatibility window. Invalid, altered, wrong-query, wrong-filter, or oversized cursors fail before search execution.
- Indexes and benchmark cases cover exact ties, duplicate variants, locale ordering, empty results, deep pages, snapshot swaps, expiry, and cursor replay.
- Numeric offsets may remain only on private bounded administrative lists whose maximum result set and consistency semantics are documented.

### D16: Versioned performance benchmark contract

- Check in a versioned benchmark manifest and deterministic corpus generator rather than relying on the small operated starter packs or undocumented local data.
- The manifest records record, pack, release, locale/script, name-length, variant, duplicate-cluster, missing-field, license, evidence, and projection-state distributions for launch-reference, 10x, and 100x profiles derived from the two-year capacity model.
- Pin query and interaction mixes for exact, prefix, fuzzy, misspelled, non-Latin, no-result, filtered, conflicting-variant, first-page, and deep-cursor search plus detail/provenance reads.
- Include controlled concurrent publication, pack ingestion, projection rebuild, tracker, and anonymous-read traffic so search is not benchmarked only in isolation.
- Measure cold and warm cache separately at PostgreSQL, FastAPI, same-origin proxy, and edge/browser boundaries. Record reference hardware, database configuration, connection ceiling, software versions, and cache preparation.
- Report p50, p95, p99, error and timeout rates, judged relevance, memory high-water mark, connections, index size/build time, job age, and projection lag. Averages alone do not pass a gate.
- Store versioned machine-readable results, environment metadata, query seeds, and representative `EXPLAIN (ANALYZE, BUFFERS)` plans as benchmark artifacts.
- The dedicated-search-engine spike starts only after the same pinned PostgreSQL profile misses the agreed gate in two reproducible runs or threatens the write-side capacity envelope. Contract and corpus changes require reviewed version updates.

### D17: Validated global PostgreSQL connection capacity contract

- Declare one deployment-level PostgreSQL connection ceiling and reserve explicit headroom for migrations, recovery, administration, monitoring, and failover before allocating application pools.
- Maintain a versioned capacity manifest with each process role's replica count, `pool_size`, zero unbudgeted overflow, acquisition timeout, statement timeout, worker concurrency, and maximum in-flight database sections.
- Deployment preflight validates the sum of `replicas * role pool` plus reserved headroom against the ceiling. Invalid configurations do not deploy or start claiming work.
- Build every SQLAlchemy engine with explicit role settings. Export active, idle, waiting, timed-out, and acquisition-latency metrics attributed by role and deployment.
- Workers acquire connections only for bounded transactional reads/writes, release them before forge, storage, OCR, signer, or registry calls, and stop claiming new work when their role budget is saturated.
- Web requests have bounded acquisition time and a typed overload response with safe retry guidance. They do not wait indefinitely or borrow recovery headroom.
- Scaling a role or changing concurrency requires updating and reviewing the capacity manifest plus rerunning the mixed-workload benchmark.
- PgBouncer may be introduced after measurement, but it does not replace role budgets, bounded transactions, or backpressure tests.
